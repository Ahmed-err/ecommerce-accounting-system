# P3.3 Orders

## Audit (code + CI screenshots of `/admin/orders`, desktop + phone, 2026-10-14; local dev server unusable on this machine)

**Status changes (A-26)**
1. Any staff role can move any order to any status in one tap: a cashier can cancel a DELIVERED order, which puts the stock back and reverses the sale. Nothing asks for confirmation.
2. Errors from a status change are ignored. The button just stops, and the user isn't told why.
3. Taking an order back out of CANCELLED is allowed for every role and re-books the sale.

**Returns (A-25)**
4. The staff return form takes the price from the browser and doesn't check it against the order, so staff can refund any amount. The customer form does check.
5. Quantities are checked against the ordered quantity only, not against earlier returns, so the same item can be returned twice.
6. Approving a return puts the stock back but doesn't book the refund in accounting.
7. Cancelling an order after a return was approved puts the returned stock back a second time.
8. The return window is 14 days from `updatedAt`, which moves whenever staff touch the order (carried over from P2.6 #14). There is no delivery date.
9. The customer form defaults to "store credit", but the shop has no store-credit system.

**Dead code**
10. `order-management.js` (`processRefund` with no cap and no checks, A-24; `updateOrderDetails`; `getOrderForEdit`), `components/admin/OrderTable.js` and `createReturnRequestAction` in `user-orders.js` aren't used anywhere. A-24 is closed by removing them.

**Numbers (`src/lib/orders.js`)**
11. "Today's orders" sums only DELIVERED orders, so its money line reads "-ج.س". The reports tab also counts only DELIVERED, while the dashboard (P3.1) counts every order except cancelled. Each screen gives a different sales figure.
12. The POS daily summary counts cancelled orders as revenue.

**UI (`OrdersModuleClient.js`)**
13. Digits are mixed: dates and totals use Arabic-Indic digits (٢٠٢٦، ١٥٫٦٠٠), but the KPI cards use Western digits. The rest of the admin uses Western digits.
14. On phone the orders table needs a sideways scroll: only the order number, date and source are visible.
15. The order detail shows the payment method as raw text ("CASH ON DELIVERY"), "Guest" in English and English product names. It has no shipping/discount/coupon breakdown and no customer notes.
16. The date filters show the browser's "mm/dd/yyyy".
17. The returns tab uses dark-theme colours (`text-red-200`, `text-emerald-400/90`), which are hard to read in light mode.

## Plan (one PR, `rebuild/p3-3-orders`)

- **Status rules, test-first:** `src/lib/order-status.js` holds one table of allowed moves per role. Forward path: PENDING → PROCESSING → SHIPPED → DELIVERED. Cancel only before delivery. Reinstating a cancelled order and cancelling a shipped one are admin/manager only. A delivered order changes only through a return. The server enforces the table, and the detail sheet shows only the allowed buttons, asks before cancelling, and shows the error if a change fails.
- **Delivery date:** add a nullable `Order.deliveredAt` (additive migration, applied on deploy), set when an order becomes DELIVERED. Existing delivered orders fall back to `updatedAt`. Customer returns count 14 days from it.
- **Returns, test-first:** one shared check for staff and customer returns. Price comes from the order line; quantity is capped at ordered minus already returned (pending + approved). Approving a return books the refund as an OUTGOING transaction ("Refund"). Cancelling an order puts back only the stock that wasn't already returned.
- **Remove dead code** (#10).
- **Numbers:** one rule everywhere: sales = orders not cancelled (as on the dashboard). This applies to today/month, reports and the POS summary.
- **UI:** Western digits; cards instead of the table on phone; Arabic payment method, customer and product names; a totals breakdown (items, shipping, discount, coupon) and customer notes in the detail; light-theme colours in returns. Same look, no redesign.

2. Approving a return books the refund in accounting automatically. **Recommended: yes.**
3. Refund methods: **(a, recommended)** cash and bank transfer only (remove "store credit", since there is no credit system); or (b) keep store credit as a label only.
